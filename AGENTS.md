# Alpha Hex Builder

## Active Unity frontier

The user approved returning active development to Unity on 2026-10-11. Open the repository root with the pinned Unity editor. `godot/` preserves the released Godot demo and its tests; it is a compatibility reference, not the active implementation.

- Read `docs/DESIGN.md` and `docs/slices/002-clay-and-first-metal.md` before changing progression.
- Preserve manual crews, gradual migration, permanent discovery, finite deposits, reserved inputs and in-flight goods. Import Godot schema 3 and Unity schemas 1/2 without writing to the source file.
- The current slice adds clay, bricks and manual primitive smelting before efficient foundries. Armies, boats, animals, multiplayer and weeks of content remain future scope.

Build a Unity game about gathering, mining, refining and territorial expansion. The current terrain is layered hex columns with staged quarry excavation. It does not support arbitrary tunnels. No PvP or multiplayer is implemented. Preserve these boundaries unless the user changes the scope.

## Project

- Open the repository root as a Unity project. Read `ProjectSettings/ProjectVersion.txt` for the editor pin.
- Read `README.md` and `docs/ARCHITECTURE.md` before changing behavior.
- Game rules belong in `Assets/AlphaHex/Scripts/Core`. Keep this assembly free of Unity references and compatible with C# 9 and .NET Standard 2.1.
- The scene, input and HUD belong in `Assets/AlphaHex/Scripts/Runtime`. They issue validated `Simulation.Try*` commands; do not directly award resources in UI code.
- Save data consists of serializable public fields. Unity uses `JsonUtility`; do not introduce dictionaries, polymorphic serialization, or `System.Text.Json` into Core/runtime without changing the persistence design deliberately.
- `tools/SimulationChecks` links the actual Core source. It is a .NET 10 console verifier, not a second game implementation.
- All visual assets are currently generated by code. The starter scene contains the bootstrap. Editor setup creates URP configuration/material assets on first import; commit those generated assets and their `.meta` files after opening Unity.
- Preserve `.meta` GUIDs. Never commit `Library`, `Temp`, `Builds`, credentials, signing certificates or machine-specific editor paths.

## Verification

Run `dotnet run --project tools/SimulationChecks/SimulationChecks.csproj --configuration Release` after changing game rules or serialization. Run `python3 tools/validate_repo.py` after moving or adding Unity assets. Check new `.meta` files into Git.

For Unity API, input, scene, rendering or build changes, run an editor compile/Play Mode check when Unity is available. Use the Unity EditMode tests for real `JsonUtility` coverage. If the editor or device is unavailable, say exactly which checks were and were not performed. A passing console suite is not proof that an iOS build works.

## Design guardrails

Keep costs, finite-resource accounting, reserved smelter input, in-flight cargo and save continuity consistent. A producer waits for its own delivery, so road length affects throughput. Preserve the manual-gather recovery path. Update the HUD and `docs/DESIGN.md` when changing balance constants.

Favor a complete small production loop before adding more resources, multiplayer, combat, fluid simulation or underground navigation. Keep project instructions and limitations accurate rather than presenting planned features as implemented.
